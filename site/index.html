01

Qué es

EOS guarda el contrato del repositorio: qué se pidió, qué se probó y quién autorizó el cambio. El código, los commits y las especificaciones quedan en inglés profesional. La interfaz puede hablar el idioma de quien opera.

No es un monorepo a escala de hiperescalador ni una base de datos global. Es un plano de control local, con barreras de escritura y evidencia de comando.

  1. Especificar

    Propuesta, especificación, diseño y tareas antes de un cambio que no sea trivial.

  2. Probar

    Primero un test que falla. Después el código mínimo. node --test o npm test.

  3. Aprobación humana

    Merge, producción, pagos y datos personales se detienen en una persona.

02

Para quién

Para quien quiere un entorno de trabajo gobernado y no un agente suelto dentro del editor. Valentín dirige el alcance. EOS ejecuta dentro de ese alcance y deja el recibo.

  • Operadores que cambian de IDE sin cambiar las reglas del repositorio.
  • Agentes que deben leer la especificación antes de escribir.
  • Revisión humana cuando el cambio sale del sandbox.

04

Tres compuertas reales

Especificación

Sin contrato aprobado no hay feature de producto. Un arreglo local y acotado no finge una ceremonia.

Pruebas

Un comportamiento nuevo entra con un test que falla. El escudo de este corte vive fuera del kernel y se prueba con Node.

Aprobación humana

La autonomía LEVEL_2 no fusiona sola, no empuja a main y no repara producción sin una persona.

05

Si verify:strict falla, no hay promoción

En .github/workflows/ci.yml el job verify ejecuta node scripts/verify-eos.js --strict. El job test ejecuta npm test. Esos pasos no llevan continue-on-error. Si el proceso sale distinto de cero, el check queda rojo.

El workflow de release gate no despliega: registra production_deploy: false. Un check verde no declara PRODUCTION_READY. La protección de ramas en GitHub, fuera de este archivo, queda sin verificar desde aquí.

El detalle está en docs/releases/VERIFY_FAILS_BLOCK_PROMOTION.md.
