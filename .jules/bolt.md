## 2024-05-14 - fs.readFileSync blocking Event Loop
**Learning:** Found multiple usages of `fs.readFileSync` in the application code, which may block the node event loop in the production codebase (or during frequent calls). While node `readFileSync` is faster for micro-benchmarks or CLI tools, we should use async alternatives for the web or heavy-duty servers to keep the Node.js event loop unblocked (as remembered from the initial knowledge). However, `src/core/llm/model-router.js` uses `fs.readFileSync` on every initialization to read the `.missions` or routing configs. There is an opportunity to cache the routing configuration or use async loads if we restructure it. Another simpler option is a memoize on `loadRoutingSsot` to prevent re-reading the file continuously if it's called multiple times per run.

Let's look at caching the file read in `loadRoutingSsot` in `src/core/llm/model-router.js` to avoid hitting the disk synchronously repeatedly, which is a significant optimization in Node.js architectures that spawn many routers or parse documents repeatedly.
